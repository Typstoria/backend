# Межі та вимоги до бекенду

Статус: v0.1, 18.10.2026. Погоджений обсяг — перший і другий етапи бачення. Дослідницький третій етап відокремлено.

## 1. Призначення

Typstoria зберігає технічну документацію у вигляді Typst-проєктів, компілює PDF і надає зовнішнім ШІ-клієнтам контрольований доступ через MCP. Діалог із моделлю відбувається у вибраному користувачем зовнішньому клієнті. Бекенд не викликає LLM для написання тексту й не потребує ключів мовних моделей.

Ключовий сценарій: користувач створює проєкт, додає контекст і матеріали, підключає MCP-клієнт; ШІ читає дозволені дані, готує окрему пропозицію, перевіряє PDF; користувач переглядає diff і результат та вирішує, що прийняти.

## 2. Погоджені правила

- Мова та фреймворк: TypeScript + NestJS.
- ORM: TypeORM із явними міграціями та вимкненим synchronize. Локально лише PostgreSQL працює в Docker, API запускається на host. Для реалізованих endpoints обов'язкова документація Swagger/OpenAPI.
- Ціль — доступний через інтернет сервер із кількома незалежними обліковими записами.
- Звичайні проєкти приватні, власник один. Спільне одночасне редагування різними користувачами не заявлено.
- Усі зміни основного проєкту від ШІ проходять через пропозицію та підтвердження у вебінтерфейсі. Це поширюється на файли, контекст і запропоновані анотації.
- Через MCP немає операцій прийняття власної пропозиції, видалення облікового запису чи керування чужими доступами.
- Помилковий Typst можна зберегти вручну. ШІ-пропозицію з помилкою компіляції можна прийняти після окремого явного підтвердження.
- Зовнішня Git-інтеграція передає резервну копію з Typstoria в GitHub. Зворотної синхронізації немає.
- «Універсальний MCP» означає стандартний інтерфейс без прив'язки до конкретного постачальника моделі. Сумісність конкретних клієнтів підтверджується тестами, а не гарантується для будь-якої програми.

## 4. Точні межі першої повної поставки

Типи ресурсів документа: `.typ`, растрові зображення, SVG, PDF, `.bib`, `.yml/.yaml`, `.json`, `.csv`, `.txt`, `.md`, `.csl`; список уточнюється перевіркою можливостей Typst. Забороняється виконувати вкладені програми, скрипти збірки та Git hooks із проєкту.

Контекстні матеріали: текстові формати, PDF із текстовим шаром і таблиці CSV/XLSX. Для XLSX зчитуються значення та обмежений набір метаданих, формули/макроси не виконуються. PDF без текстового шару зберігається, але позначається як такий, що не має текстового витягу. OCR не входить до цієї поставки. Оригінали доступні авторизованому клієнту незалежно від наявності витягу.

Для структури документа розрізняємо позиції у вихідному тексті та обчислені заголовки Typst. Їхні відмінності описано у файлі 04; regex сам по собі не вважається достатнім парсером.

Пакети Typst і шрифти підтримуються через контрольований каталог із зафіксованими версіями. Компіляція не завантажує довільні залежності з інтернету. Механізм поповнення каталогу — серверна адміністративна операція.

## 5. Поза погодженою поставкою

- Вбудований ШІ-чат, вибір/оплата LLM і гарантії якості згенерованого тексту.
- LaTeX, локальний агент користувача та розширення VS Code зі SmartTeX.
- Спільні ролі editor/viewer, організації, CRDT/OT та live collaboration.
- Автоматичне двостороннє Git-об'єднання.
- OCR і довільні інтеграції зовнішніх сховищ.
- Автоматичне визначення походження інформації та семантичної застарілості документа — третій, дослідницький етап. У моделі зберігаються стабільні ID і ревізії для майбутнього розширення.

## 6. Критерій завершення

Проміжна версія з одним файлом є інкрементом розробки. Повна поставка завершена лише після F01–F19 і N01–N06: функціональні сценарії, негативні перевірки, робочий OAuth/MCP, відновлення резервної копії та серверна демонстрація. Календарні строки й доступність розробників ще не визначені.
