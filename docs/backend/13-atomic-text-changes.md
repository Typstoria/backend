# Атомарні зміни текстових файлів і контексту

Статус: реалізований атомарний save P2 для текстів, контексту й завантажених ресурсів. Staging та скачування описані у [14-resource-uploads.md](14-resource-uploads.md). Компіляція прийнятих ревізій описана у [15-compilation.md](15-compilation.md). Git writer/history/restore реалізовані у [16-git-history.md](16-git-history.md). Контекстні матеріали ще не реалізовані.

## 1. Контракт

У Swagger для request body є окремі examples: оновлення тексту, додавання розділу, переміщення файла, заміна entrypoint, зміна контексту, додавання й заміна ресурсу. Вибери потрібний сценарій; ID у прикладах демонстраційні й мають бути замінені на значення з `/state`.

`POST /api/projects/:projectId/changes` потребує чинну вебсесію з підтвердженою поштою та `Idempotency-Key`. MCP direct write заборонений також в application service. Успіх повертає 201: одна прийнята ревізія для всього набору, якщо manifest змінився; інакше повертається поточна ревізія без нових snapshot/audit/Git записів. Некомпільований Typst дозволений; цей endpoint не запускає компілятор.

```json
{
  "baseRevisionId": 1,
  "summary": "Оновлено вступ і додано розділ",
  "operations": [
    { "type": "updateText", "fileId": 1, "content": "= Документ\n#include \"chapter.typ\"" },
    { "type": "createFile", "path": "chapter.typ", "content": "== Вступ\nТекст розділу." },
    { "type": "updateContext", "content": "Документ українською мовою." }
  ]
}
```

Числові ID у прикладі потрібно замінити на отримані від create/state. `summary` необов'язковий, типово `Updated project`; якщо заданий, обрізається по краях і має містити 1–500 символів без керівних символів. Невідомі поля, невідомі типи операцій та некоректні типи значень відхиляються до application service.

| Операція        | Поля                 | Поведінка                                                                        |
| --------------- | -------------------- | -------------------------------------------------------------------------------- |
| `createFile`    | `path`, `content`    | Новий текстовий файл зі сталим числовим ID                                       |
| `updateText`    | `fileId`, `content`  | Повна заміна тексту файла цієї ревізії                                           |
| `renameFile`    | `fileId`, `path`     | Перейменування або переміщення; ID та байти зберігаються                         |
| `deleteFile`    | `fileId`             | Видалення зі складу нового знімка; старі ревізії залишаються доступними          |
| `setEntrypoint` | `path`               | Вибір текстового `.typ` файла в кінцевому дереві, зокрема створеного цим набором |
| `updateContext` | `content`            | Повна заміна текстового контексту                                                |
| `attachFile`    | `path`, `uploadId`   | Новий binary файл зі staged upload; новий сталий ID                              |
| `replaceFile`   | `fileId`, `uploadId` | Заміна байтів на ресурс зі staged upload; ID та шлях зберігаються                |

Операції застосовуються в заданому порядку. Повторна зміна тексту/контексту використовує останнє задане значення; ціль, уже видалену раніше в наборі, змінити не можна. Перевірка унікальності шляхів виконується для кінцевого дерева, тому два наявні файли можна атомарно поміняти шляхами. `setEntrypoint` визначається за кінцевим шляхом після всіх операцій; останній такий вибір має силу. Нові файли створюються одразу з потрібним шляхом і текстом; їхні серверні ID повертаються у відповіді.

Відповідь містить `projectId`, `revisionId`, `revisionNumber`, `mainFileId`, `manifestHash`, `historySyncStatus=pending` та `createdFiles`: масив `{fileId, path}` для нових файлів. Внутрішні snapshot IDs, blob IDs і storage keys не повертаються. `pending` означає асинхронну Git-проєкцію на момент save; актуальний статус читається через revision history або `/state`.

## 2. Цілісність і ліміти

- Шляхи — відносні POSIX, Unicode NFC. Заборонені порожні сегменти, `.`/`..`, `\`, `:`, керівні символи, `.git` та `.typstoria` у будь-якому регістрі й на будь-якій глибині.
- Максимум 1024 UTF-8 байти на шлях і 255 на сегмент. Нормалізація Unicode не може створювати дублікати. Файл не може одночасно бути директорією іншого файла.
- Головний файл завжди існує в новому знімку, має вид text і суфікс `.typ`. При його перейменуванні ID лишається головним; при видаленні або зміні розширення потрібно вибрати дійсний entrypoint у тому самому наборі.
- Текст і контекст — коректний Unicode без NUL, до 1 MiB UTF-8 байтів кожен. Порожній текст дозволений. Ресурси завантажуються окремим multipart запитом до 10 MiB; кінцеве розширення binary файла має відповідати виявленому формату.
- До 200 операцій у запиті, до 500 файлів та 64 MiB у поточному знімку включно з контекстом. Історичні ревізії не перезаписуються.
- JSON body цього маршруту обмежений 8 MiB з урахуванням JSON escaping. Решта JSON-маршрутів зберігає загальний ліміт 1 MiB; multipart uploads мають окремий ліміт 10 MiB на файл. Розмір body додатково обмежує кількість великих текстів в одному запиті.

Невірна структура DTO дає 400. Небезпечний шлях, недійсний file ID у межах ревізії, дублікати чи неправильний entrypoint — 422 з відповідним `error.code`. Перевищення розмірів — 413. Чужий/видалений проєкт — 404 без розкриття його стану.

## 3. Транзакція та конфлікти

Після ownership/idempotency/base перевірок сервер читає незмінний базовий знімок, будує й перевіряє кінцеве дерево в пам'яті. Байти нових/оновлених текстів публікуються у приватному blob storage перед DB-транзакцією. Незмінені файли повторно використовують наявні blobs; context-only save не звертається до storage. Binary файли використовують уже опубліковані upload blobs. MIME зберігається у кожному SnapshotFile, тому однакові байти можуть незалежно використовуватися як text і binary.

Коротка транзакція блокує рядок Project, повторно перевіряє доступ/видалення, завершений idempotency result та `currentRevisionId=baseRevisionId`. Далі створює IDs нових файлів, blob metadata, snapshot зі всіма файлами, прийняту ревізію з parent/base та наступним номером, оновлює current revision і записує audit `project.saved`, pending Git mapping та результат запиту. Uploads можна повторно використовувати до expiry; consume-стан відсутній. Назва проєкту не змінюється.

Два незалежні saves з однією базою дають один успіх і один 409 `REVISION_CONFLICT` із `error.details.currentRevisionId`. Frontend зберігає локальний draft, перечитує стан і пропонує порівняння; автоматично повторювати старий текст із новим base ID не можна. Видалення під час staging дає 404 при повторній перевірці, а конкурентне перейменування проєкту не губиться.

Помилка будь-якого DB-запису відкочує весь набір, включно з current revision, file IDs, audit/Git mapping та idempotency result. При storage failure повертається 503 без зміни ревізії. Після невдалої спроби той самий ключ доступний для повтору. Зовнішні staged bytes після rollback/conflict можуть залишитися без DB-посилань до майбутнього GC.

## 4. Повтори та міграція

`Idempotency-Key` має ті самі обмеження, що й create. Область ключа — вебсесія та конкретний маршрут проєкту. Однакові ключі для create, різних проєктів чи сесій незалежні. Payload hash враховує base ID, summary та впорядковані операції; порядок властивостей JSON-об'єктів не впливає на hash.

Повтор успішного запиту повертає той самий записаний результат **до перевірки застарілої бази**, навіть якщо вже існують наступні ревізії. Він не звертається до storage і не додає audit/Git mapping чи ревізію. Інший payload з тим самим ключем дає 409 `IDEMPOTENCY_CONFLICT`. Authentication та ownership/активність проєкту перевіряються перед replay.

Міграція `GeneralizeProjectIdempotency` перейменовує `project_creations` на `idempotency_records`, додає область операції та записану відповідь. Старі create keys/hashes зберігаються, відповіді відновлюються з ревізії №1. Кількість таблиць не збільшується. Відкат міграції відмовляє, якщо вже є результати non-create операцій, щоб не втратити захист їхніх повторів.

## 5. Читання та перевірка

`GET /api/projects/:id/state?revisionId=…` повертає дерево, entrypoint і контекст вибраної прийнятої ревізії; без параметра — поточної. Поле `project.currentRevisionId` завжди описує актуальну картку проєкту, а `revision.id` — вибрану ревізію. Текст файла читається через наявний `/files/:fileId?revisionId=…`. Revision ID іншого проєкту дає 404. Дерево та blob metadata читаються одним join-запитом без окремого запиту на кожен файл.

```bash
npm run migration:run
npm run check
npm run test:integration
```

Тести перевіряють multi-file атомарність, сталі ID при переміщенні, історичне читання, заміну entrypoint, context-only save, конкурентні saves, payload-order/replay, ізоляцію проєктів/сесій, небезпечні шляхи та квоти, відкликання доступу, storage/DB failures, видалення/перейменування під час staging та збереження старих ключів міграцією.
